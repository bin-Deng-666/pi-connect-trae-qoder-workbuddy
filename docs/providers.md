# Providers

What each provider needs from your machine, and the wire details that make it work. Read the section for the providers you actually use — nothing here is needed to run the others.

## Trae

### What it needs

| Thing | Where it comes from | Why |
|---|---|---|
| Credential | `~/.dsh/.trae-auth.cn.json` | The desktop client's own login, refreshed by it |
| Device fingerprint | `~/Library/Application Support/Trae CN/User/globalStorage/storage.json` | Upstream treats a changing machine id on one token as a stolen token |
| App version | `/Applications/Trae CN.app/Contents/Resources/app/product.json` | Some request headers must carry the timestamped version code |
| Model catalog | generated by `npm run catalog` | See below |

The credential file is written by the `dsh-connect-trae` plugin. If you do not run that plugin, log in to the Trae app and copy its `Cloud-IDE-JWT` token into that file yourself:

```json
{ "credentials": [{ "accessToken": "<jwt>", "edition": "cn", "expiresAtMs": 0, "accountName": "you" }] }
```

### Why a generated catalog is unavoidable

Trae names a model **twice** per chat request:

```json
{ "model": "glm-5.3", "config_name": "glm-5.3", "function": "solo_agent_remote" }
```

`model` and `function` are not derivable from each other. The same model id appears in several picker groups, each served by a different wire function with a different context window and different capabilities — `solo_work_lite` gives 200K, `solo_agent_remote` gives up to 1M. Guessing `function` from the model name routes some models to an endpoint that does not serve them.

So the mapping is read from the one place that has the truth for your machine and your login: the desktop client's picker cache, in the SQLite database at

```
~/Library/Application Support/Trae CN/User/globalStorage/state.vscdb
```

under the key `3041714748265068:AI.agent.model.model_list_map`. Each group in that JSON is an array of models; the **group name is the wire function**.

```bash
npm run catalog                                    # default: Trae CN, solo_agent_remote
node bin/catalog.mjs --app "TRAE SOLO CN"          # a different install
node bin/catalog.mjs --group solo_work_lite        # a different picker group
node bin/catalog.mjs --stdout                      # inspect before writing
```

The generated file (`~/.pi/agent/trae-models.json`) is small and disposable — regenerate it whenever Trae ships new models.

### Context window

The catalog stores each model's **largest** selectable window, not its default. `context_window_size` in the client is `{default, max}` where `max` is an array of sizes the user can pick; the default is a UI preference (200K), while the largest is the actual capability (1M). Reporting the default would cap every long-conversation turn at 200K even when the model can take 1M.

### Credits

`POST https://api.trae.cn/trae/api/v2/pay/web_user_ent_usage` with `{require_usage: true}`.

**`usage_summary` is already the answer**: `total_amount − consumed_amount`, covering every bucket including gifts. Do **not** also add up `user_entitlement_pack_list` remainders. Measured on a real account, four buckets of 500/100/100/100 summed to exactly the reported `total_amount` of 800, and `consumed_amount` equalled the sum of their consumption — adding the per-bucket remainders produced exactly double the true balance.

## Qoder

### What it needs

| Thing | Where it comes from |
|---|---|
| PAT | `~/.dsh/.qoder-accounts.cn.json` |
| Nothing else | device fingerprint and session keys are derived from the PAT |

The file is written by the `dsh-connect-qoder` plugin (add a PAT in its settings card). Alternatively write it yourself:

```json
{ "accounts": [{ "pat": "<pat>", "accountName": "you", "id": "12345" }] }
```

### The protocol, briefly

Three things are non-standard and each is load-bearing:

1. **Signed bearer.** `Bearer COSY.<payloadB64>.<md5>` where the signature covers the payload, a per-session RSA-wrapped AES key, the date, the encoded body, and the path with `/algo` stripped. Every part is signed in the exact form it is sent — re-serialising the body breaks it.
2. **Custom base64.** The body is base64-encoded, the three n/3-sized blocks are rotated, then transliterated through a fixed 65-character alphabet. The server rejects a body that did not go through this, so it is reproduced rather than reasoned about.
3. **Double-wrapped SSE.** Each frame is `data: {"statusCodeValue":200,"body":"<json string>"}`. The inner string is the OpenAI-shaped chunk. A non-200 hides in the *outer* envelope, which is why an upstream error surfaces as a thrown error rather than a malformed delta.

Session setup is one `jobToken` exchange per PAT, cached until five minutes before expiry.

### Model ids

Qoder's internal ids are short codes (`dmodel`, `kmodel_latest`, `qmodel_38max`); readable names only exist in the upstream `display_name`. Pi renders `model.id`, so the config uses display names — `DeepSeek-V4-Pro`, not `dmodel`. The adapter accepts **either form**, so the same config works whether the model was picked in pi or the gateway was called directly.

`auto` is filtered out: it is a router, not a model — it picks a model and a context size server-side, so it has nothing stable to list.

### Context window

Qoder advertises 200K / 400K / 1M tiers per model. The gateway uses the largest, for the same reason as Trae: the default is a picker setting, not a capability. 1M is the real ceiling — a request above it returns HTTP 413, measured.

### Credits

`GET https://openapi.qoder.com.cn/sash/api/v2/me/usage` → `qoderUsage.userQuota.remaining + addOnQuota.remaining`. Both buckets are summed because "how much can I still use" includes purchased add-ons.

## WorkBuddy

### What it needs

| Thing | Where it comes from |
|---|---|
| Access token | `~/.dsh/workbuddy-vault/cn/*.json` (newest `refreshedAtMs` wins) |

One file per account; the newest wins because an older file is an older token and may already be revoked. Unparseable files are skipped rather than fatal.

### Why it is not proxied

Its chat endpoint is already OpenAI-compatible: same request body, same SSE shape, and the billing figure arrives in an OpenAI-shaped `usage` field. A hop through the gateway would translate nothing while adding latency and a failure mode. Point pi at it directly:

```json
"workbuddy": {
  "baseUrl": "https://copilot.tencent.com/v2",
  "api": "openai-completions",
  "apiKey": "$WORKBUDDY_TOKEN",
  "headers": {
    "User-Agent": "WorkBuddy/5.8.3 WorkBuddy/5.8.3 CLI/5.8.3",
    "X-IDE-Name": "WorkBuddy",
    "X-IDE-Type": "CLI"
  },
  "compat": { "thinkingFormat": "openai", "maxTokensField": "max_tokens", "supportsStore": false }
}
```

Those three headers are not cosmetic: WorkBuddy authenticates the **CLI** channel separately from the GUI one, and a request without them is rejected regardless of the token.

### Credits

`POST https://www.codebuddy.cn/v2/billing/meter/get-user-resource`.

**Sum `CycleCapacityRemain`, not `CapacityRemain`.** The first is what is left in the current billing cycle; the second is what is left of the bucket's lifetime, and it never moves. Measured on a trial bucket, `CapacityRemain` still read 500 while `CycleCapacityRemain` had fallen to 217.63. Upstream writes both as strings (`"217.63000011"`), so they are parsed explicitly.

## Adding a provider

1. Create `src/providers/<name>.mjs` exporting `chat(body, {emit, emitUsage, emitDone})`, `models()`, `credits()`.
2. Add it to `ADAPTERS` in `src/gateway.mjs` — that also enables its `/credits/<name>` route.
3. Add its credential path to `CREDENTIAL_FILES` in `src/config.mjs`.
4. Add the provider id to `CREDIT_PROVIDERS` in `extensions/credits/index.ts`.
5. Add a section to this file saying what breaks and why — that is the part future maintainers need most.
